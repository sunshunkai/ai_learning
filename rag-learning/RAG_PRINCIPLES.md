## 第 1 章 为什么需要 RAG

### 本章目标

- 理解大模型的知识边界从哪来。
- 理解幻觉不是单纯的模型「坏掉了」。
- 能说清 RAG、微调、长上下文、工具调用各自适合什么场景。

### 1.1 模型知道什么，不知道什么

大模型的知识来自训练数据，可以粗略分成两类：

| 类型 | 含义 | 例子 |
|---|---|---|
| 参数化知识 | 训练时被压进模型参数里的知识 | 通用常识、公开语料、常见编程知识 |
| 非参数化知识 | 模型参数里没有，需要外部提供 | 公司制度、客户资料、今天的订单状态 |

RAG 的核心判断是：**私有知识和频繁变化的知识，不应该指望模型记住。**

模型不知道某件事时，通常有三种表现：

1. 坦白说不知道，这是理想情况。
2. 给出一个过时但看起来合理的答案。
3. 编造一个格式正确、语气自信的错误答案，也就是幻觉。

### 1.2 幻觉从哪来

幻觉不是单一原因造成的，常见来源有四种：

1. **训练数据缺失**：问题涉及的知识从未出现在训练数据里。
2. **知识过时**：训练截止日期之后发生的事情，模型没有见过。
3. **上下文不足**：用户问题信息不完整，模型自行补全了缺失部分。
4. **生成目标错位**：模型被训练成「续写合理文本」，而不是「承认不知道」。

最后一点很关键：模型的默认目标是生成流畅合理的回答，
不是保证事实正确。所以我们需要在输入端提供依据，并在 Prompt 里约束它。

### 1.3 注入私有知识的四条路线

| 路线 | 做法 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|---|
| 长上下文塞入 | 把资料直接放进 Prompt | 实现最简单 | 资料多时超长、贵、易漏 | 少量、临时、单次任务 |
| RAG | 先检索再放进 Prompt | 成本可控、更新方便、可引用 | 依赖检索质量 | 知识库问答、客服、文档助手 |
| 微调 Fine-tuning | 用私有数据继续训练 | 能内化风格和模式 | 贵、慢、更新困难、仍有幻觉 | 固定风格、固定格式、领域能力 |
| 工具调用 | 让模型调用数据库/API | 实时、精确、可执行动作 | 需要工程实现 | 查订单、算价格、发邮件 |

RAG 不是万能的，它最擅长的是：

> 从大量非结构化文本里，找到与问题相关的一小部分，再让模型基于这部分作答。

### 1.4 RAG 的收益与代价

**收益：**

- 私有知识不用训练进模型。
- 文档更新后重建索引即可生效。
- 答案可以附带来源，便于核查。
- 相比微调，初始成本更低、迭代更快。

**代价：**

- 多了一次检索，系统更复杂。
- 检索质量直接决定答案质量上限。
- 需要维护文档解析、分块、索引、评测等流程。
- 文档本身可能被恶意注入 Prompt，带来安全风险。

### 1.5 什么时候不该用 RAG

- 知识只有一小段，直接放进 Prompt 更简单。
- 需要精确计算或查询实时状态，应该用工具调用。
- 目标是改变模型的表达风格，微调或 Prompt 工程更合适。
- 数据全是表格和数字，传统数据库查询往往比向量检索可靠。

### 1.6 本章小结

- RAG 解决的是「模型不知道你的私有知识」和「知识会过期」。
- 它不改变模型参数，只改变模型看到的输入。
- 幻觉只能降低，不能被彻底消除。
- 选 RAG 之前，先确认问题真的是「知识检索」问题。

### 1.7 自测题

1. 为什么模型会一本正经地说错话？
2. RAG 和微调分别改变模型的什么？
3. 用户问「我的订单到哪了」，应该用 RAG 吗？为什么？

## 第 2 章 RAG 全景架构

### 本章目标

- 能画出 RAG 的完整链路。
- 理解离线阶段和在线阶段的分工。
- 知道一次用户提问在系统里经过了哪些步骤。

### 2.1 一张总图

```text
                    离线阶段：建索引
┌──────────┐   ┌────────┐   ┌────────┐   ┌──────────┐   ┌──────────┐
│ 文档来源 │ → │ 解析   │ → │ 清洗   │ → │ 分块     │ → │ Embedding│
└──────────┘   └────────┘   └────────┘   └──────────┘   └────┬─────┘
                                                              ↓
                                                       ┌──────────┐
                                                       │ 向量库   │
                                                       └────┬─────┘
                                                            │
                    在线阶段：检索与生成                    │
┌──────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────▼─────┐
│ 用户问题 │ → │ 查询   │ → │ 向量化 │ → │ 检索   │ → │ 重排     │
└──────────┘   │ 改写   │   └────────┘   └────────┘   └────┬─────┘
               └────────┘                                   ↓
                                                    ┌──────────────┐
                                                    │ 拼装 Prompt  │
                                                    └──────┬───────┘
                                                           ↓
                                                    ┌──────────────┐
                                                    │ 大模型生成   │
                                                    └──────┬───────┘
                                                           ↓
                                                    ┌──────────────┐
                                                    │ 答案 + 引用  │
                                                    └──────────────┘
```

### 2.2 离线阶段

离线阶段的目标是把原始资料变成「可被快速、准确检索的知识」。

| 步骤 | 输入 | 输出 | 关键问题 |
|---|---|---|---|
| 数据采集 | 文档、网页、数据库 | 原始文件 | 数据从哪里来、多久更新一次 |
| 解析 | PDF、Word、HTML | 纯文本 | 格式、表格、图片怎么处理 |
| 清洗 | 纯文本 | 干净文本 | 页眉页脚、目录、重复内容怎么去 |
| 分块 | 长文本 | 多个 chunk | 块多大、按什么边界切 |
| 向量化 | chunk | 向量 + metadata | 用什么 embedding 模型 |
| 入库 | 向量 | 向量索引 | 用什么向量库、怎么支持过滤 |

离线阶段的质量决定了在线阶段的上限。检索不到正确资料时，
不要把希望寄托在「换一个更强的生成模型」上。

### 2.3 在线阶段

在线阶段的每一步都会叠加延迟，所以需要权衡效果和成本。

| 步骤 | 是否必需 | 作用 | 常见优化 |
|---|---|---|---|
| 查询改写 | 可选 | 把口语问题变成检索友好的查询 | 多查询、HyDE |
| 向量化 | 必需 | 把查询转成向量 | 缓存高频查询 |
| 检索 | 必需 | 召回候选 chunk | 混合检索、多路召回 |
| 重排 | 可选 | 提高排序精度 | 只对 Top N 重排 |
| 拼装 Prompt | 必需 | 组织上下文和约束 | 控制上下文长度 |
| 生成 | 必需 | 输出答案 | 流式输出、引用 |

### 2.4 一次请求的完整时序

用第 10 章的产品案例举例，用户问：

> 我三个月前买的年度会员，现在还能退款吗？

系统内部发生的事情：

1. 接收问题，识别用户身份和租户。
2. 查询改写为「年度会员 退款 期限 政策」。
3. 用 embedding 模型把查询转成向量。
4. 在向量库里做相似度检索，召回 Top 5。
5. 用 metadata 过滤掉不属于当前租户、未发布版本的文档。
6. 用 rerank 模型重新排序，保留 Top 3。
7. 把 Top 3 的内容、来源、用户问题拼成 Prompt。
8. 大模型依据上下文生成答案。
9. 返回答案，并附上「退款政策.md」等来源。
10. 记录日志：问题、召回结果、分数、最终答案，供评测和排查。

第 10 步经常被忽略，但它是系统可持续迭代的基础。

### 2.5 关键角色

| 角色 | 职责 | 对应组件 |
|---|---|---|
| 文档解析器 | 把各种格式变成文本 | PyPDF、python-docx、Unstructured |
| 分块器 | 把长文本切成合理片段 | RecursiveCharacterTextSplitter |
| Embedding 模型 | 把文本转成向量 | BGE、DashScope、OpenAI Embeddings |
| 向量库 | 存储和检索向量 | Chroma、FAISS、Milvus、pgvector |
| 检索器 | 封装检索策略 | LangChain Retriever |
| 重排模型 | 精细排序候选 | BGE Reranker、Cohere Rerank |
| 生成模型 | 基于上下文作答 | DeepSeek、Qwen、GPT、Claude |
| 评测系统 | 衡量改动效果 | RAGAS、自建评测集 |

### 2.6 本章小结

- RAG 分成离线建索引和在线检索生成两段。
- 离线阶段决定「知识库里有什么、以什么粒度存在」。
- 在线阶段决定「这次能查到什么、模型能看到什么」。
- 检索质量是答案质量的上限。

### 2.7 自测题

1. 用户提问时，离线阶段会重新执行吗？
2. 为什么同一个 embedding 模型在建库和查询时都要用？
3. 日志里应该记录哪些信息，才能定位「检索错了」还是「生成错了」？

## 第 3 章 数据准备：从文档到可检索知识

### 本章目标

- 知道哪些数据适合进知识库。
- 理解解析、清洗、元数据设计的关键决策。
- 能设计一个支持权限和更新的知识库结构。

### 3.1 数据源盘点

先不要急着写代码，先把数据源列清楚：

| 数据源 | 格式 | 更新频率 | 是否结构化 | 处理难度 |
|---|---|---|---|---|
| 产品手册 | PDF | 每月 | 半结构化 | 中 |
| 客服 SOP | Markdown | 每周 | 结构化 | 低 |
| 历史工单 | 数据库 | 实时 | 结构化 | 高 |
| 官网 FAQ | HTML | 每月 | 半结构化 | 低 |
| 会议纪要 | Word | 每周 | 非结构化 | 高 |

不同数据源适合不同的检索策略。FAQ 适合一问一答；
产品手册适合章节检索；表格数据更适合结构化查询。

### 3.2 解析

解析的目标是把各种格式变成带结构的纯文本。常见问题：

- PDF 双栏排版被错误拼接。
- 页眉页脚混入正文。
- 表格被解析成无意义的字符流。
- 扫描件没有文本层，需要 OCR。
- 图片和图表里的信息完全丢失。

解析质量差的表现是：检索时明明有资料，分数却很低，
因为正确内容被切成了无语义的碎片。

### 3.3 清洗

清洗不是可选项，常见的清洗动作：

1. 去掉页眉、页脚、页码。
2. 去掉目录、封面、免责声明等重复模板。
3. 合并被换行拆开的句子。
4. 统一全角/半角、空格和标点。
5. 去掉完全重复的段落。

清洗的原则是：**保留语义，去掉噪声，不要为了干净而误删信息。**

### 3.4 元数据设计

metadata 不参与向量相似度计算，但它决定检索时能不能过滤、答案能不能引用。

| 字段 | 作用 | 例子 |
|---|---|---|
| `source` | 来源文件名 | `退款政策.md` |
| `page` | 页码 | `3` |
| `section` | 所属章节 | `第二章 退款规则` |
| `updated_at` | 更新时间 | `2026-08-01` |
| `tenant_id` | 租户隔离 | `customer_a` |
| `status` | 发布状态 | `published` |
| `doc_type` | 文档类型 | `policy`、`faq` |
| `version` | 版本号 | `v2` |

有了这些字段，检索时才能做到：

```text
只查 tenant_id = customer_a 且 status = published 且 doc_type = policy 的文档
```

### 3.5 权限与租户隔离

权限问题必须在检索层解决，而不是靠 Prompt 里写「不要泄露其他客户资料」。

三种常见策略：

1. **物理隔离**：每个租户一个独立知识库或 collection。
2. **逻辑隔离**：同一个库，用 metadata 过滤 `tenant_id`。
3. **混合隔离**：敏感数据物理隔离，公共数据共享。

如果用户属于多个权限组，检索时要先计算可见范围，再传过滤条件。

### 3.6 文档更新策略

文档是会变的，RAG 系统必须有更新机制：

- **全量重建**：简单可靠，但文档多时很慢、很贵。
- **增量更新**：按文档 ID 更新、删除对应 chunk 再重建。
- **双版本切换**：先建新索引，验证无误后切流量。

无论哪种方式，都要能回答：

1. 文档改了，旧 chunk 怎么删除？
2. 文档删了，向量库里怎么同步删除？
3. 索引更新失败，线上会不会查到半成品？

### 3.7 本章小结

- 数据准备的质量直接决定 RAG 的上限。
- 解析和清洗的目标是保留语义、去掉噪声。
- metadata 决定过滤、引用、更新和权限能力。
- 权限过滤必须做在检索层。

### 3.8 自测题

1. 为什么 PDF 解析不好会让检索质量变差？
2. `source` 和 `tenant_id` 分别解决什么问题？
3. 文档更新后，为什么必须处理旧 chunk？

## 第 4 章 分块 Chunking

### 本章目标

- 理解为什么必须分块。
- 掌握 `chunk_size` 和 `chunk_overlap` 的取舍。
- 知道常见切分策略和中文场景的注意事项。

### 4.1 为什么要分块

有三个现实约束：

1. 模型上下文窗口有限，不能无限塞资料。
2. 整篇文档做 embedding 会稀释主题，检索不精确。
3. 上下文越长，成本和延迟越高。

所以要把长文档切成语义相对完整的小块。

### 4.2 三种切分策略

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 固定长度 | 每 N 个字符切一刀 | 简单、快 | 容易切断句子和语义 |
| 递归切分 | 按段落、句子、标点逐级尝试 | 平衡质量与简单 | 仍然依赖分隔符质量 |
| 语义切分 | 用模型判断语义边界 | 边界更自然 | 慢、贵、实现复杂 |

本仓库 `02_chunking.py` 使用的 `RecursiveCharacterTextSplitter` 属于递归切分。

### 4.3 chunk_size 和 chunk_overlap

| 参数 | 含义 | 调大的效果 | 调小的效果 |
|---|---|---|---|
| `chunk_size` | 每块多大 | 上下文更完整，但检索变粗 | 检索更精确，但上下文易丢 |
| `chunk_overlap` | 相邻块重叠 | 边界答案不易丢，但冗余多 | 省空间，但跨段答案易断 |

经验起点：

- 中文 FAQ、客服政策：`chunk_size` 300 到 800 字。
- 技术文档：`chunk_size` 500 到 1000 字。
- `chunk_overlap`：约为 `chunk_size` 的 10% 到 20%。

这些只是起点，最终要靠评测集决定。

### 4.4 中文分块的特殊问题

英文按单词和空格切分很自然，中文没有空格，需要注意：

1. 分隔符要包含中文标点：`。！？；，`。
2. 不要按字符数硬切，否则会把一句话切成两半。
3. 标题和正文最好放在同一个 chunk，或把标题写入 metadata。

### 4.5 进阶分块策略

**父子块（Small-to-Big）：**

用小 chunk 做检索，命中后再取它所属的大块交给模型。
这样检索精确，生成时上下文又完整。

**句子窗口：**

命中某一句后，额外把前后相邻句子一起放进上下文。

**结构化分块：**

按 Markdown 标题、HTML 标签、PDF 章节切分，让每个 chunk 对应一个完整小节。

**上下文增强：**

给每个 chunk 补充它所属的标题或摘要，例如：

```text
【退款政策 > 年度会员 > 退款期限】
年度会员超过 30 天原则上不支持退款……
```

### 4.6 怎么判断分块是否合理

不要凭感觉。做三件事：

1. 随机抽 20 个 chunk，看它们是否语义完整。
2. 用评测问题跑检索，看正确 chunk 有没有被召回。
3. 只改 `chunk_size`，对比 `Recall@K` 和答案质量。

### 4.7 常见误区

- 所有文档用同一个 `chunk_size`，不区分 FAQ 和长篇手册。
- `chunk_overlap` 设为 0，跨段答案永远检索不到。
- chunk 太小，一块只有一句话，模型看不到上下文。
- chunk 太大，一块包含多个主题，检索分数虚高但内容不精确。

### 4.8 本章小结

- 分块是检索质量和生成质量之间的第一道平衡。
- 优先按语义边界切，其次才是固定长度。
- 用小 chunk 检索、大 chunk 生成，是常见的折中方案。
- 参数要用评测集验证，不要照抄别人的值。

2. 为什么「一块只有一句话」可能不是好事？
3. 父子块策略为什么能同时改善检索和生成？

## 第 5 章 Embedding 向量化

### 本章目标

- 理解向量、维度、相似度的直觉。
- 知道如何选择 embedding 模型。
- 掌握建库和查询必须保持一致的原则。

### 5.1 从文字到向量

Embedding 模型把一段文本映射成一串数字，例如 768 维或 1024 维向量。
语义相近的文本，在向量空间里的方向更接近。

```text
"年度会员退款"        -> [0.12, -0.03, 0.88, ...]
"会员退费规则"        -> [0.11, -0.02, 0.85, ...]   距离近
"发票开具流程"        -> [-0.40, 0.71, 0.05, ...]   距离远
```

注意：向量本身不可读，但可以用距离判断语义相似度。

### 5.2 相似度怎么算

最常见的度量是余弦相似度（Cosine Similarity）：

```text
cos(A, B) = A · B / (|A| × |B|)
```

- 结果接近 1：方向几乎一致，语义相近。
- 结果接近 0：几乎无关。
- 结果接近 -1：语义相反。

如果向量已经归一化，余弦相似度就等于点积，计算更快。

### 5.3 模型选型

| 类型 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 本地模型 | BGE、M3E、GTE | 免费、数据不出境 | 需要机器资源、要自己部署 |
| 云端模型 | DashScope、OpenAI | 省事、质量稳定 | 按量收费、数据出网 |
| 教学用 hash | 本仓库 `03_embeddings_hash.py` | 离线、确定性 | 不理解语义，只适合跑通流程 |

中文场景常见选择：

- `BAAI/bge-small-zh-v1.5`：轻量，适合入门和本地部署。
- `BAAI/bge-m3`：多语言、长文本支持较好，资源占用更高。
- 云端 embedding：适合快速上线，注意成本和数据合规。

### 5.4 对称检索和非对称检索

- **对称检索**：问题找问题，例如「怎么退款」找「如何退费」。
- **非对称检索**：短问题找长文档，这是 RAG 的常态。

部分模型对非对称检索要求给 query 加指令前缀，例如 BGE 系列曾建议：

```text
为这个句子生成表示以用于检索相关文章：年度会员退款
```

是否需要前缀、前缀具体是什么，要以你使用的模型说明为准。
`bge-m3` 一般不需要这类前缀。

### 5.5 三条一致性原则

1. 建库和查询必须用同一个 embedding 模型。
2. 向量维度和归一化方式必须一致。
3. 相似度算法必须和训练时预期的度量方式一致。

违反任何一条，都会出现「明明语义相同，分数却很低」。

### 5.6 成本与性能

- Embedding 只在建库和查询时调用，通常比生成模型便宜。
- 文档没变时，不要重复 embedding。
- 高频 query 可以缓存 embedding 结果。
- 批量 embedding 比逐条调用更省时间。

### 5.7 常见误区

- 建库用云端模型，查询用本地模型，导致向量空间不匹配。
- 以为向量维度越高效果一定越好，忽略成本和速度。
- 用 hash embedding 的检索结果来评估真实业务效果。
- 忽略模型对输入长度的限制，长文本被静默截断。

### 5.8 本章小结

- Embedding 把语义相似度变成可计算的向量距离。
- 模型选型要同时考虑语言、成本、部署和数据合规。
- 建库和查询的一致性是硬性要求。
- 教学用的 hash embedding 不能代表真实效果。

2. 为什么不能建库和查询用不同的 embedding 模型？
3. 非对称检索和对称检索有什么区别？

## 第 6 章 向量库与索引

### 本章目标

- 理解向量库的职责和选型标准。
- 知道 HNSW、IVF 等索引算法解决什么问题。
- 理解 metadata 过滤和索引更新的重要性。

### 6.1 向量库做什么

向量库至少要提供四个能力：

1. 存储向量和原始文本。
2. 支持相似度检索。
3. 支持 metadata 过滤。
4. 支持增删改和持久化。

它不只是「存一堆向量」，还承担了检索、过滤和生命周期管理的职责。

### 6.2 常见选型

| 方案 | 特点 | 适合场景 |
|---|---|---|
| 内存向量库 | 进程内、重启即丢 | 教学、测试、小数据 |
| Chroma | 本地、易用、可持久化 | 原型、中小规模 |
| FAISS | 高性能、纯索引库 | 本地大规模检索 |
| pgvector | 和 PostgreSQL 一起用 | 已有关系型数据库的团队 |
| Milvus | 分布式、功能完整 | 大规模生产环境 |
| Qdrant | 过滤和检索能力较强 | 生产中需要复杂过滤 |

本仓库对应：

- `06_vectorstore_memory.py`：内存向量库。
- `07_vectorstore_chroma.py`：Chroma 持久化。
- `08_vectorstore_faiss.py`：FAISS 本地索引。

### 6.3 索引算法在解决什么

如果每次检索都和全量向量逐一比较，数据量大时无法接受。
近似最近邻（ANN）索引用少量精度换取速度：

| 算法 | 思路 | 特点 |
|---|---|---|
| Flat | 暴力精确比较 | 最准，最慢，适合小数据 |
| IVF | 先聚类再局部搜索 | 建索引快，需要调 `nprobe` |
| HNSW | 分层图导航 | 查询快、召回高，占内存 |
| PQ | 向量压缩 | 省内存，精度有损 |

入门阶段不用自己实现，但要知道：**索引参数会影响召回率。**
检索不到时，除了怪分块和 embedding，也要检查索引配置。

### 6.4 metadata 过滤

过滤有两种时机：

- **先过滤再检索**：先缩小范围，再算相似度，速度快、安全。
- **先检索再过滤**：可能召回一堆被过滤掉的结果，导致有效结果不足。

生产环境优先选择「先过滤再检索」，尤其在多租户场景。

### 6.5 持久化与重建

需要明确几个问题：

1. 服务重启后索引还在不在？
2. 文档更新后，旧向量怎么删除？
3. 重建索引期间，线上查询走哪个版本？
4. 索引文件和数据库备份怎么恢复？

### 6.6 常见误区

- 用内存向量库上了生产，重启后知识库空了。
- 只按向量检索，忽略 metadata 过滤，导致越权。
- 文档删除后不清理旧向量，旧答案一直存在。
- 索引算法参数不当，导致召回率下降却找不到原因。

### 6.7 本章小结

- 向量库负责存储、检索、过滤和生命周期管理。
- 选型要看数据量、过滤需求、持久化和运维能力。
- ANN 索引用精度换速度，参数会影响召回率。
- 多租户场景必须在检索层做权限过滤。

### 6.8 自测题

1. 内存向量库为什么不适合生产环境？
2. HNSW 和 Flat 索引的取舍是什么？
3. 为什么多租户系统必须做 metadata 过滤？

## 第 7 章 检索 Retrieval

### 本章目标

- 理解检索的完整流程。
- 掌握 Top K、分数阈值、混合检索的作用。
- 能定位「检索不到」和「检索不准」的原因。

### 7.1 检索的基本流程

```text
用户问题 -> (可选改写) -> 查询向量 -> 相似度检索 -> Top K 候选
        -> (可选 rerank) -> 最终上下文
```

### 7.2 Top K 和分数阈值

| 参数 | 含义 | 调大的效果 | 调小的效果 |
|---|---|---|---|
| Top K | 取回多少条候选 | 召回更全，但噪声和成本增加 | 更聚焦，但可能漏资料 |
| 分数阈值 | 低于多少分不返回 | 过滤更严，可能漏召回 | 保留更多，但引入噪声 |

一个常见组合是：先召回 20 条，rerank 后取 3 到 5 条。

### 7.3 三种检索方式对比

| 方式 | 原理 | 擅长 | 不擅长 |
|---|---|---|---|
| 向量检索 | 语义相似度 | 口语化提问、同义表达 | 精确编号、专有名词 |
| 关键词检索 | BM25、全文索引 | 错误码、产品型号、人名 | 换个说法就检索不到 |
| 混合检索 | 两者融合 | 大多数生产场景 | 配置和调优更复杂 |

### 7.4 混合检索与 RRF

混合检索的常见做法是：

1. 向量检索取一份排名。
2. 关键词检索取一份排名。
3. 用 Reciprocal Rank Fusion（RRF）融合。

RRF 的思路很简单：

```text
score = Σ 1 / (k + rank)
```

`k` 通常取 60 左右。它不依赖两路分数的绝对值，只看排名，
所以对分数尺度不同的检索器比较友好。

### 7.5 多路召回

同一个问题可以用不同方式召回：

- 原始 query。
- 改写后的 query。
- 关键词 query。
- HyDE 生成的假设答案。

多路召回能提高覆盖率，但会增加延迟和成本，需要重排或融合来收尾。

### 7.6 检索诊断

出现问题时，按这个顺序查：

1. **数据在不在**：原始文档里到底有没有这条知识？
2. **有没有被切碎**：正确内容在哪个 chunk，chunk 是否语义完整？
3. **能不能被表示**：embedding 模型是否理解这类词汇？
4. **有没有被召回**：正确 chunk 在 Top K 里排第几？
5. **有没有被过滤**：metadata 条件是否把它排除了？
6. **有没有被重排挤掉**：rerank 后它还在不在？

把这六步做成日志，比反复换模型有效得多。

### 7.7 本章小结

- 检索的目标是把正确资料放进候选集，并尽量排到前面。
- Top K 和阈值是召回率与噪声之间的平衡。
- 向量检索和关键词检索互补，生产环境常用混合检索。
- 排查检索问题要看「在哪一步丢掉的」。

3. 正确资料在向量库里但没出现在答案里，可能有哪些原因？

## 第 8 章 查询改写与重排

### 本章目标

- 理解用户问题和检索查询不是一回事。
- 掌握常见查询改写方法和 Rerank 的作用。
- 知道什么时候该引入这些复杂度。

### 8.1 为什么问题不等于查询

用户说的话往往不适合直接检索：

```text
用户问题：我上个月买的那个会员还能退吗，急！
检索查询：年度会员 退款 期限 政策
```

原问题包含口语、指代和情绪，检索查询更接近知识库的表述方式。

### 8.2 常见查询改写方法

| 方法 | 做法 | 适合场景 |
|---|---|---|
| 同义词扩展 | 补充近义词、别称 | 专有名词、行业术语 |
| 指代消解 | 把「那个」替换成具体对象 | 多轮对话 |
| 多查询 | 生成 3 个不同角度的查询 | 一个问题有多个说法 |
| 查询分解 | 把复杂问题拆成子问题 | 多跳推理 |
| HyDE | 先生成假设答案，再拿答案去检索 | 短问题、专业问题 |

### 8.3 多查询

例如用户问「退款要多久到账？」，可以生成：

```text
退款到账时间
退款处理周期
原路退回需要几天
```

三路都检索，再合并去重。它提高召回率，但会让延迟成倍增加。

### 8.4 HyDE

HyDE（Hypothetical Document Embeddings）先让模型生成一段「假设的答案文档」，
再用这段文档去检索。因为答案文档和知识库文献的写法更接近，
向量匹配往往更好。

代价是多一次模型调用，而且假设答案可能把检索带偏。

### 8.5 Rerank

向量检索是「双塔」结构：query 和 chunk 分别编码，快但精度有限。
Rerank 是「交叉编码」：把 query 和 chunk 放在一起打分，慢但更准。

典型用法：

```text
向量召回 20 条 -> Rerank 重新打分 -> 取前 3 到 5 条
```

常用模型：BGE Reranker、Cohere Rerank、Jina Reranker。
需要注意上下文长度限制和延迟成本。

### 8.6 组合顺序

一个实用的在线链路是：

```text
原始 query + 改写 query + 关键词 query
        -> 多路召回
        -> 去重 + RRF 融合
        -> Rerank
        -> 取 Top N 交给模型
```

不是所有系统都需要这么复杂。先用最简单的链路跑通，
再用评测数据证明每一层确实带来收益。

### 8.7 本章小结

- 用户问题和检索查询需要解耦。
- 查询改写提高召回率，重排提高排序精度。
- 每增加一层都会增加延迟和成本，要有数据支撑。
- 先用简单链路，再按需加复杂度。

### 8.8 自测题

1. 为什么多轮对话里需要指代消解？
2. Rerank 和向量检索的本质区别是什么？
3. 什么情况下不值得引入多查询？

## 第 9 章 生成 Generation

### 本章目标

- 理解 Prompt 的组成和上下文组织方式。
- 学会约束模型「只依据资料回答」。
- 知道引用、拒答和上下文长度怎么处理。

### 9.1 Prompt 的四个部分

一个工程化的 RAG Prompt 通常包含：

```text
[角色与任务]
你是一个售后政策助手。

[行为约束]
只根据下面的资料回答问题。
如果资料不足，明确说明「资料中没有相关信息」，不要推测。
回答时标注来源。

[检索到的资料]
[来源：退款政策.md，第 2 节]
年度会员超过 30 天原则上不支持退款……

[用户问题]
我三个月前买的年度会员，现在还能退款吗？
```

### 9.2 上下文怎么组织

- 按相关性从高到低排列，把最重要的放在前面或最后。
- 每条资料标注来源，方便模型引用和后续核查。
- 去掉重复和明显无关的 chunk，减少噪声。
- 控制总长度，不要把上下文窗口塞满。

### 9.3 强制引用

引用有两种常见做法：

1. 让模型在答案中写出来源名称。
2. 由系统根据实际使用的 chunk 自动附上来源。

第二种更可靠，因为模型可能编造来源。
更严格的做法是让模型输出结构化的 `answer + citations`，
再由后端校验引用是否来自本次检索结果。

### 9.4 拒答与不确定性

一个负责任的 RAG 系统要能说「不知道」。Prompt 里可以写：

```text
如果检索资料没有覆盖问题，请回答：
「根据现有资料无法确定，建议咨询人工客服。」
不要根据常识补充资料中没有的信息。
```

拒答率高不一定是坏事，关键看是「该拒答时拒答」还是「有资料也拒答」。

### 9.5 上下文长度与成本

- 上下文越长，输入 token 成本越高、延迟越大。
- 内容太多会稀释重点，模型可能忽略关键信息。
- 不能把所有召回结果都塞进去，要靠 Top K 和重排控制。

### 9.6 生成侧的常见问题

| 现象 | 可能原因 | 处理方向 |
|---|---|---|
| 答案编造 | Prompt 没约束、上下文不足 | 强化拒答约束、提高检索质量 |
| 答案漏掉关键点 | 上下文太长、关键内容排序靠后 | 重排、压缩上下文 |
| 引用不对 | 让模型自由生成引用 | 系统侧回填引用 |
| 口径不一致 | 多个文档说法冲突 | 建立文档优先级和版本治理 |
| 答案太啰嗦 | Prompt 没有格式要求 | 明确输出结构和长度 |

### 9.7 本章小结

- RAG 的生成质量建立在上游检索质量之上。
- Prompt 要同时约束「依据什么回答」和「没有依据怎么办」。
- 引用最好由系统校验和回填。
- 拒答能力是系统可靠性的组成部分。

### 9.8 自测题

1. 为什么让模型自己生成引用可能不可靠？
2. Prompt 里为什么必须写「资料不足时怎么办」？
3. 上下文塞得越多，答案一定越好吗？

## 第 10 章 完整产品案例：Dify 售后客服助手

### 本章目标

- 把前面所有概念串成一个可落地的产品方案。
- 理解 Dify 知识库各配置项对应的原理。
- 能照着案例设计自己的知识库问答系统。

### 10.1 业务目标

场景：在线课程平台的售后客服。

痛点：

- 退款、发票、换绑等政策分散在十几份文档里。
- 客服靠记忆和搜索，答案不一致。
- 新人培训周期长，重复问题占用大量人力。

目标：做一个「售后政策助手」，回答问题时给出依据，资料不足时转人工。

### 10.2 知识库设计

```text
knowledge/
├── 退款政策.md
├── 会员权益说明.md
├── 发票规则.md
├── 账号与换绑规则.md
└── 售后SOP.md
```

每条文档的 metadata 至少包含：

| 字段 | 值示例 |
|---|---|
| `source` | `退款政策.md` |
| `section` | `年度会员退款` |
| `updated_at` | `2026-08-01` |
| `status` | `published` |
| `tenant_id` | `default` |

### 10.3 离线阶段：在 Dify 里建知识库

1. 新建知识库，上传上述文档。
2. 选择索引方式：
   - 高质量模式使用 embedding 做语义检索，是 RAG 主路径。
   - 经济模式主要依赖关键词索引，成本低但语义能力弱。
3. 设置分段：
   - 最大分段长度：中文先试 300 到 800 字。
   - 分段重叠：约为分段长度的 10% 左右。
   - 分段标识符：优先按标题、空行、中文句号切。
4. 选择 embedding 模型，等待解析、分块、向量化和入库完成。
5. 使用召回测试输入问题，观察命中的分段和分数，必要时回到第 3 步调整。

### 10.4 在线阶段：一个问题的完整追踪

用户提问：

> 我三个月前买的年度会员，现在还能退款吗？

**步骤 1：识别身份与租户。**

系统确定用户属于哪个租户，只在可见文档范围内检索。

**步骤 2：查询改写。**

```text
年度会员 退款 期限 政策
```

**步骤 3：向量化。**

用知识库同一个 embedding 模型把查询转成向量。

**步骤 4：检索。**

假设召回 Top 5：

| 排名 | 来源 | 内容节选 | 相似度 |
|---|---|---|---|
| 1 | 退款政策.md | 年度会员超过 30 天原则上不支持退款 | 0.86 |
| 2 | 退款政策.md | 30 天内可按剩余月份比例退款 | 0.81 |
| 3 | 售后SOP.md | 特殊情况需人工审核并提交工单 | 0.72 |
| 4 | 会员权益说明.md | 年度会员含 12 个月服务期 | 0.55 |
| 5 | 发票规则.md | 退款后发票需要冲红处理 | 0.31 |

**步骤 5：重排。**

Rerank 模型重新打分，前三条保留，第 5 条被剔除。

**步骤 6：拼装 Prompt。**

把保留的分段、来源和用户问题放进 Prompt，并加上约束。

**步骤 7：生成并引用。**

期望答案：

> 根据退款政策，年度会员超过 30 天原则上不支持退款；如果你在购买后
> 30 天内申请，可以按剩余月份比例退款。你的情况已超过 30 天，
> 如有特殊情况需要人工审核，建议提交工单。
>
> 来源：退款政策.md、售后SOP.md

### 10.5 Prompt 模板

```text
你是一个售后政策助手。请只根据下面的资料回答用户问题。

规则：
1. 资料中没有的信息，不要推测。
2. 如果资料不足，回答「根据现有资料无法确定，建议转人工客服」。
3. 回答后列出你依据的来源。
4. 用简洁、礼貌的中文回答。

资料：
{context}

用户问题：
{question}
```

### 10.6 Dify 关键参数的含义

| 设置 | 作用 | 调大的后果 | 调小的后果 |
|---|---|---|---|
| 分段长度 | 每块承载的信息量 | 重点被稀释，检索变粗 | 上下文被切断 |
| 分段重叠 | 避免边界切断答案 | 冗余多、成本上升 | 跨段答案易丢 |
| Top K | 交给模型的候选数 | 噪声增加、成本上升 | 可能漏资料 |
| 分数阈值 | 过滤低相关结果 | 容易召回不足 | 容易引入无关内容 |
| Rerank | 精细排序 | 延迟和成本增加 | 排序依赖向量检索 |
| 混合检索 | 语义 + 关键词 | 调优更复杂 | 专有名词易检索失败 |

版本提示：部分 Dify 版本中，Vector Search 和 Full-Text Search 的 Top K
与 Score Threshold 只在启用 Rerank 后生效，默认分数阈值是 0.5。
实际行为以你使用的 Dify 版本文档为准。

### 10.7 效果验证

准备 30 到 100 条真实客服问题，标注正确答案和正确来源，然后：

1. 看正确文档有没有被召回。
2. 看答案是否只依据资料。
3. 看引用是否准确。
4. 看资料不足时是否会拒答。

### 10.8 上线后的维护

- 文档变更后触发索引更新。
- 定期抽查问答日志，发现新的失败模式。
- 把高频未命中问题加入评测集。
- 政策更新时保留版本，避免新旧规则混用。

### 10.9 案例复盘

这个案例里最关键的不是「用了哪个大模型」，而是：

1. 政策文档被正确解析和分块。
2. 查询能匹配到政策原文。
3. 检索范围受租户和版本约束。
4. Prompt 明确要求依据资料回答。
5. 有评测集能证明改动是否有效。

### 10.10 自测题

1. 如果把「三个月前」当成关键词去检索，可能匹配到什么？
2. 为什么要把「来源」和「原文」一起展示给用户？
3. 文档更新后不重建索引会发生什么？

## 第 11 章 参数调优

### 本章目标

- 建立「先指标、后调参」的思维方式。
- 知道每个参数影响链路中的哪一环。
- 掌握典型问题的调参顺序。

### 11.1 先指标，后调参

没有评测集的调参是盲调。至少要能回答：

- 这次改动让哪个指标变好了？
- 有没有让别的指标变差？
- 改动值不值得增加的成本和延迟？

### 11.2 参数地图

| 参数 | 影响环节 | 主要影响 |
|---|---|---|
| `chunk_size` | 离线分块 | 召回粒度、上下文完整性 |
| `chunk_overlap` | 离线分块 | 边界信息丢失 |
| embedding 模型 | 离线 + 在线 | 语义匹配能力 |
| 索引算法参数 | 离线索引 | 召回率、速度、内存 |
| `top_k` | 在线检索 | 召回率、噪声、成本 |
| 分数阈值 | 在线检索 | 噪声、漏召回 |
| 检索方式 | 在线检索 | 语义 vs 精确匹配 |
| rerank 模型 | 在线重排 | 排序精度、延迟 |
| Prompt 模板 | 生成 | 忠实度、引用、拒答 |
| 生成模型 | 生成 | 表达能力、成本、速度 |

### 11.3 推荐调参顺序

1. 先确保数据解析和分块正确。
2. 再确认 embedding 和索引能召回正确 chunk。
3. 然后调 Top K 和阈值。
4. 再考虑混合检索和 Rerank。
5. 最后调 Prompt 和生成模型。

顺序不能反。检索都没有正确资料，调 Prompt 是在错误的地基上装修。

### 11.4 常见处方

| 症状 | 优先调整 |
|---|---|
| 有资料但检索不到 | 分块、embedding、混合检索 |
| 检索到太多无关内容 | 阈值、Top K、Rerank |
| 答案只答了一半 | overlap、父子块、Top K |
| 专有名词检索不准 | 混合检索、关键词权重 |
| 多轮对话检索跑偏 | 指代消解、查询改写 |
| 答案编造 | Prompt 约束、拒答、引用校验 |
| 成本太高 | 缓存、减少召回、模型降级 |

### 11.5 常见反模式

- 同时改五个参数，结果无法归因。
- 用没有标注的数据判断好坏。
- 只测成功案例，不测边界和拒答。
- 为了追求召回率，把 Top K 调到很大。
- 频繁更换模型，却不修复数据质量问题。

### 11.6 本章小结

- 调参要按链路顺序来，先检索后生成。
- 每次只改一个变量，用评测集对比。
- 参数没有通用最优值，只有针对你数据的较优值。

### 11.7 自测题

1. 为什么不应该先调 Prompt？
2. 同时改多个参数有什么问题？
3. 提高 Top K 一定会让答案更好吗？

## 第 12 章 RAG 评测

### 本章目标

- 理解为什么必须建立评测集。
- 掌握检索侧和生成侧的常用指标。
- 能设计一个可持续的回归测试流程。

### 12.1 为什么需要评测

主观感觉不可靠：

- 你容易记住成功案例，忘记失败案例。
- 换模型后可能某类问题变好，另一类变差。
- 没有基线，无法判断改动是否真的有效。

评测集是 RAG 系统的体检表。

### 12.2 评测集怎么造

一条评测样本至少包含：

```text
问题：年度会员超过 30 天还能退款吗？
标准答案：原则上不支持，特殊情况需人工审核。
正确来源：退款政策.md 第 2 节
难度：中
类型：政策
```

采集渠道：

- 真实客服问题。
- 产品文档 FAQ。
- 人工设计的边界问题。
- 故意问知识库里没有的问题，用来测试拒答。

建议先做 30 到 50 条，覆盖主要场景，再逐步扩充。

### 12.3 检索指标

| 指标 | 含义 | 关注点 |
|---|---|---|
| Recall@K | 正确 chunk 是否出现在前 K 条 | 有没有找到 |
| Hit Rate | 至少命中一条正确结果的比例 | 覆盖率 |
| MRR | 第一条正确结果排名的倒数均值 | 排得靠不靠前 |
| NDCG | 考虑排序位置的加权指标 | 整体排序质量 |
| Precision@K | 前 K 条里有多少是相关的 | 噪声比例 |

如果 Recall@K 就低，优先修检索；如果 Recall@K 高但答案差，修排序和生成。

### 12.4 生成指标

| 指标 | 含义 |
|---|---|
| 忠实度 Faithfulness | 答案是否完全由检索资料支持 |
| 答案相关性 Answer Relevancy | 答案是否回答了用户问题 |
| 上下文精确率 | 检索到的内容有多少真正有用 |
| 引用准确率 | 引用来源是否真的支持对应结论 |
| 拒答正确率 | 该拒答时拒答、不该拒答时不拒答 |

### 12.5 端到端评测

端到端看的是用户是否解决问题，常用方式：

- 人工评分，1 到 5 分。
- 双人标注，计算一致性。
- 用大模型做初筛，再由人工复核。

### 12.6 用 LLM 做评审的注意事项

- 评审模型和生成模型最好不同，减少同源偏好。
- 评审标准要写成明确规则，而不是「好不好」。
- 定期用人工标注校准评审模型。
- 不要让评审模型看到候选答案顺序，避免位置偏差。

### 12.7 回归测试流程

```text
改动代码/参数 -> 跑评测集 -> 对比基线 -> 达标则合并 -> 否则回退或继续调
```

把评测脚本放进 CI，每次改动都跑一遍，能避免「修好一个问题、弄坏三个问题」。

### 12.8 本章小结

- 没有评测集的优化都是猜。
- 检索指标和生成指标要分开看。
- 评测集要包含边界问题和无答案问题。
- 评测应该自动化、可回归。

### 12.9 自测题

1. Recall@K 和忠实度分别衡量什么？
2. 为什么评测集里要有「知识库回答不了」的问题？
3. 为什么不应完全依赖 LLM 评审？

## 第 13 章 进阶架构

### 本章目标

- 知道基础 RAG 之外还有哪些改进方向。
- 理解每种进阶方案解决的具体问题。
- 能判断什么时候值得引入这些复杂度。

### 13.1 Advanced RAG 的三种位置

改进可以发生在三个阶段：

| 阶段 | 改进方向 |
|---|---|
| 索引前 | 数据清洗、分块、上下文增强 |
| 检索时 | 混合检索、多路召回、查询改写 |
| 检索后 | 重排、压缩、过滤 |

### 13.2 Contextual Retrieval

Anthropic 提出的一种思路：在 embedding 之前，先让模型为每个 chunk
补充它所在的上下文说明，再进行索引。

好处是 chunk 不再孤立，检索时更容易理解它属于哪个章节、讨论什么主题。
代价是建索引时需要额外模型调用。

### 13.3 GraphRAG

把文档中的实体和关系抽取成图，适合回答「A 和 B 有什么关系」
这类需要多跳推理的问题。它比向量检索更擅长全局结构性问题，
但构建和维护成本高。

### 13.4 Agentic RAG

让 Agent 自己决定：

- 需不需要检索。
- 检索什么。
- 结果够不够。
- 不够就改写查询再检索。
- 是否需要调用其他工具。

适合复杂、多步、需要判断的场景。代价是延迟和不确定性更高。

### 13.5 多模态 RAG

除了文本，还可以检索图片、表格、音频和视频。
常见做法是用多模态 embedding 把图片和文本映射到同一空间，
或者在检索后把图片交给多模态模型理解。

### 13.6 什么时候引入进阶方案

判断标准只有一条：**基础方案在评测集上卡在哪个环节。**

| 瓶颈 | 可以考虑 |
|---|---|
| 召回不到 | 混合检索、查询改写、上下文增强 |
| 排序不准 | Rerank |
| 跨文档推理弱 | GraphRAG、查询分解 |
| 问题太复杂 | Agentic RAG |
| 非文本资料多 | 多模态 RAG |

### 13.7 本章小结

- 进阶方案的目的是解决具体瓶颈，不是为了堆技术。
- 先做基础 RAG，再用评测定位瓶颈。
- 复杂度越高，延迟、成本和维护成本越高。

### 13.8 自测题

1. Rerank 属于检索前、检索时还是检索后？
2. GraphRAG 擅长什么类型的问题？
3. 什么时候应该从基础 RAG 升级到 Agentic RAG？

## 第 15 章 术语、清单与 FAQ

### 本章目标

- 提供一份可以随时查阅的速查表。
- 上线前逐项检查。
- 回答学习中最容易混淆的问题。

### 15.1 术语表

| 术语 | 英文 | 含义 |
|---|---|---|
| RAG | Retrieval-Augmented Generation | 检索增强生成 |
| Chunk | Chunk | 分块后的文本片段 |
| Embedding | Embedding | 文本到向量的映射 |
| 向量库 | Vector Store | 存储和检索向量的系统 |
| 召回 | Recall | 从知识库取回候选资料 |
| 重排 | Rerank | 对候选结果重新排序 |
| Top K | Top K | 取回前 K 条结果 |
| 阈值 | Score Threshold | 低于该分数的结果不返回 |
| 混合检索 | Hybrid Search | 向量检索与关键词检索结合 |
| 查询改写 | Query Rewriting | 把问题改写成更适合检索的形式 |
| 幻觉 | Hallucination | 模型生成看似合理但不正确的信息 |
| 忠实度 | Faithfulness | 答案是否由检索资料支持 |
| 父子块 | Small-to-Big | 小片段检索、大片段生成 |
| Agentic RAG | Agentic RAG | 由 Agent 决定检索策略的 RAG |
| GraphRAG | GraphRAG | 基于知识图谱的 RAG |

### 15.3 常见问题 FAQ

**Q1：RAG 能完全消除幻觉吗？**

不能。RAG 能显著降低幻觉，但检索错误、上下文冲突、Prompt 约束不足
仍会导致错误答案。

**Q2：RAG 和微调应该选哪个？**

需要外部知识和频繁更新，选 RAG；需要改变风格、格式或领域能力，
考虑微调。两者也可以结合。

**Q3：向量库越大越好吗？**

不是。数据质量、分块和检索策略比单纯堆数据更重要。

**Q4：Top K 应该设多少？**

没有统一答案。常见做法是先召回 10 到 20 条，重排后取 3 到 5 条，
再用评测集微调。

**Q5：中文一定要用中文 embedding 吗？**

优先选中文或多语言表现好的模型。模型对目标语言的语义理解能力
直接决定检索效果。

**Q6：为什么要用 rerank，向量检索不够吗？**

向量检索快但排序较粗，Rerank 更准但更慢。先召回再重排是常见的
效果和性能折中。

**Q7：知识库文档应该多久更新一次？**

根据业务变化频率决定。政策类建议有变更就触发更新，
并保留版本和发布时间。

**Q8：RAG 系统上线后怎么持续变好？**

收集真实问题和失败案例，加入评测集，按评测结果优化，
而不是凭感觉换模型。

### 15.5 全手册总结

RAG 的本质是一条链路：

```text
好数据 -> 好分块 -> 好向量 -> 好检索 -> 好排序 -> 好上下文 -> 好答案
```

每一环都会限制后面的上限。学习时不要只盯着生成模型，
而要从数据、检索、生成、评测四个层面建立完整视角。
